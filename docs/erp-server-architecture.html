1Executive summary

The ERP Server is a single-deployable NestJS monolith that provides the master-data, inventory, accounting and sales backbone for a multi-company, multi-branch retail ERP. It is a mature, internally consistent codebase: 77,701 lines of TypeScript across 69 controllers and 87 services, backed by 90 PostgreSQL models spread over eight schemas and 204 sequential migrations. Its defining architectural choice is that a large part of the user interface — grids, dropdowns, column layouts, and the SQL that feeds them — is data, not code.

1.1What the system is

Functionally the platform covers the master-data and stock spine of a distribution ERP: an item catalogue with units, conversions, barcodes, taxes and price levels; a chart of accounts with a voucher engine; customers, suppliers and the geographic hierarchy above them; warehouses, opening stock, physical stock counts and a batch-level stock ledger; and the organisational structure — companies, branches, fiscal years, employees and users — that scopes all of it.

Two design decisions distinguish it from a conventional CRUD service. First, customers and suppliers are account ledgers: each one is provisioned with a row in acc_ledger_master and reuses that ledger's primary key as its own, so a customer is its ledger rather than pointing at one. Second, the configured-SQL engine stores the SELECT statement behind every grid and dropdown as a database row, parses and validates it at runtime, binds tenant parameters into it, and executes it on a read-only connection pool. Screens can be added or reshaped by an administrator without a deployment.

The application currently has authentication but no authorisation. 2System context and scope

2.1Position in the wider system

The ERP Server is the sole backend for the ERP product. It is consumed by a browser-based administration and point-of-sale client over HTTP, and it owns the PostgreSQL database outright — there is no other writer. Redis is an optional dependency used for HTTP response caching, authentication sessions and BullMQ job transport; the application degrades to a no-op cache and boots successfully when Redis is absent.

Convention — no ORM lock-in on the read path

Prisma owns every typed CRUD path. 4Runtime architecture

4.1Layering

The application is a layered monolith. Controllers are thin — they validate, delegate, and shape the response envelope. Services hold the domain logic and own transaction boundaries. Two persistence services sit beneath them, and a set of global cross-cutting components wraps every request from the outside.

4.2The request pipeline

Every request passes through a fixed chain assembled in src/main.ts and src/app.module.ts. The order is load-bearing: body limits are registered before Nest initialises so they override the framework's 100 kB default, and the access-token guard runs before any interceptor so that request context is populated from the verified token — never from a header — before caching or handler logic sees the request.

4.3Bootstrap sequence

src/main.ts performs a deterministic 13-step boot. Two aspects are worth recording because they shape deployment. First, src/env.preload.ts is imported before reflect-metadata and before AppModule, so process.env is fully populated for module-evaluation-time reads — several modules (notably the throttler) read process.env directly rather than through ConfigService. Second, path resolution is pkg-aware: resolveFilePath() searches the working directory, then the executable's directory, then the packaged snapshot, so TLS certificates can sit beside the binary.

6API design and contracts

6.1URL grammar

All routes are versioned by URI under a configurable prefix: /{API_PREFIX}/v{API_VERSION}/{resource}/{action}, in practice /api/v1/…. The house style is verb-in-path CRUD rather than resource REST, and it is applied with near-total consistency across the master modules:

POST   /api/v1/item-groups/create     → upsert: creates when no id is supplied, updates when one is
GET    /api/v1/item-groups/get        → single record by id (query param)
GET    /api/v1/item-groups/list       → paginated list: ?search=&page=&limit=
DELETE /api/v1/item-groups/delete     → toggles the soft-delete flag; returns { id, deleted: boolean }

Across the codebase this yields get ×64, delete ×54, create ×51 and list ×10 as the dominant sub-paths. The trade-off is deliberate but should be stated plainly: the API is not idiomatic REST, so HTTP caching, conditional requests and standard client tooling gain little from the method semantics. Two controllers (users, physical-stock) additionally expose :id-style routes as aliases, which is the only place the two styles collide.

6.2Response envelopes

Successful responses are assembled by hand in each controller — there is no global response interceptor — against a shared type, ModuleApiSuccessResponse:

{
  "success": true,
  "message": "Item groups fetched successfully",
  "data": [ … ],
  "meta":  { "page": 1, "limit": 20, "total": 3, "total_pages": 1 },
  "styles": [ … ]        // optional: grid column styling, when served by the configured-SQL engine
}

Two endpoints deliberately break the envelope: GET /health returns a bare status object, and POST /auth/login|refresh return a bare token payload.

Defect — the error contract is not uniform

There are two error envelopes, and which one a client receives depends on whether the controller declares a module-scoped exception filter. Fifty-six controllers do, and return {success:false, message, errors:[{field, message}]} — with no status code, path or timestamp in the body. The remaining thirteen — including auth, health and users — fall through to the global AllExceptionsFilter and return {success:false, statusCode, message, path, timestamp}, where message may be a string, an array of strings, or a nested object. A client cannot parse errors uniformly. Consolidating on one envelope is a low-risk, high-value fix (§16).

A further subtlety worth knowing when debugging: the module filter derives the field name in each error by running a regular expression over the validation message (each module supplies its own field-name pattern, e.g. /\b(arm[A-Za-z0-9]+)\b/ for Area). When no match is found the field is reported as the literal string "request".

Convention — null versus undefined in DTOs

The shared decorator library encodes a three-state update semantics that is easy to miss and important to preserve: undefined means do not touch this column, while an explicit null means clear it. This is implemented by SkipOnNullish() — a ValidateIf that suppresses validation only for nullish values — wrapped into every Nullable* decorator. Partial updates therefore work without a separate PATCH DTO.

7Data architecture

Ninety models across eight PostgreSQL schemas, generated from 92 hand-maintained schema fragments and evolved through 204 sequential migrations. The schema is master-data dominated — roughly 75 of the 90 models are masters or configuration — with transactional depth concentrated in the voucher stack, the stock ledger and quotations.

7.1Schema composition — the generated schema is not the source of truth

prisma/schema.prisma (4,803 lines) is a build artefact. It is regenerated by scripts/build-prisma-schema.js, which recursively walks prisma/, concatenates base.prisma with every other fragment in path-alphabetical order, and stamps each with a provenance comment. Editing the generated file is futile — it is rebuilt before every Prisma command, including postinstall.

// AUTO-GENERATED FILE. DO NOT EDIT.
// Generated by scripts/build-prisma-schema.js

// ----- prisma/inventory/itemMaster.prisma -----
model ItemMaster { … }

The pipeline enforces one invariant with a hard failure: only base.prisma may declare a generator or datasource block. A fragment that tries to raises an error and aborts the build. This keeps the datasource — and the 12-schema declaration — in exactly one place.

Convention — where to make a schema change

Edit the fragment under prisma/<domain>/*.prisma, never prisma/schema.prisma. Then run npm run prisma:migrate:dev, which rebuilds the schema before invoking Prisma. Every Prisma npm script is wired this way, so a stale generated schema is structurally impossible.

7.2The multi-schema model

Twelve PostgreSQL schemas are declared in the datasource; eight are actually populated. Every model carries an explicit @@schema(...). Note that the folder layout does not map one-to-one onto schemas — prisma/dropdown/ models are annotated @@schema("fixed"), and prisma/stocks/ maps to the singular stock.

7.3Modelling conventions

The schema is written in a legacy-ERP idiom that is applied uniformly. Understanding these six conventions is enough to read any table in the system.

ConventionRule, and how consistently it holds
Column prefixesEvery column is prefixed with a per-table abbreviation — item_*, avh_*, cus_*, sup_*, grid_*, seq_*. Prisma fields are camelCase, mapped with an explicit @map to snake_case. This is also why configured-SQL parameters are prefixed p_* — so a parameter token can never be mistaken for a real column.
Primary keys72 models use @default(dbgenerated("uuidv7()")) @db.Uuid — time-ordered UUIDs, validated at the edge with ParseUUIDPipe({version:'7'}). This requires a uuidv7() function to exist in the database; it is a hard deployment prerequisite. Fourteen small lookup tables use autoincrement().
Soft delete80 of 90 models carry an *_is_deleted boolean. Enforcement is application-level: there is no Prisma middleware or extension applying it, so every read must filter explicitly. Frequently paired with an independent *_is_active flag (68 models) — a two-axis lifecycle where deleted means invisible and inactive means visible but unusable.
Audit columns*_created_on (83 models), *_created_by (82), *_modified_on (58), *_modified_by (56), all Timestamptz(6). The actor is not injected by middleware — services read it from RequestContextService.getUserId() and write it explicitly, falling back to a sentinel DEFAULT_ACTOR UUID of all zeroes when no user is present.
Tenancy columns34 models carry *_company_id and 36 carry *_branch_id; branch is usually nullable, meaning "shared across branches". Composite indexes follow the scope, e.g. @@index([companyId, branchId, accYear]).
Linked ledgerCustomers and suppliers share a primary key with an acc_ledger_master row: the ledger is created first inside the transaction and its led_id becomes the master's own id. Field propagation is table-driven by a copy-map; updates and soft-deletes are mirrored. This is the single most important non-obvious invariant in the schema.
Critical — tenant isolation is not enforced anywhere

The tenancy columns exist, but nothing applies them. A Prisma client extension (src/database/prisma/tenant-scope.extension.ts) that auto-scoped 35 models to requestContext.getCompanyId() on every findMany, findFirst, count, aggregate, groupBy, updateMany and deleteMany was deleted in commit 80ab8eb and never replaced. There is no row-level security in the database either. Isolation now depends entirely on each service — and each stored grid_sql — remembering to apply the predicate, and most services do not. A stale comment in items-master.service.ts:602 still tells the reader that "reads are auto-scoped to the token's company (see tenant-scope.extension.ts)". They are not. See R2, §15.

7.4Migration strategy

204 migrations run from 20260212000000_init to 20260713072139_… — roughly 1.3 migrations per calendar day over five months, which is the signature of a schema still being actively discovered rather than maintained. Deployment uses prisma migrate deploy (aliased as npm run migration:run).

Migrations are not only DDL. Several rewrite rows in fixed.grid_details.grid_sql to schema-qualify table names after models moved between schemas. That practice — editing data with migrations, then correcting the migration in place — produced the need for two bespoke repair scripts, both of which are worth understanding before operating this system:

ScriptProblem it exists to solve
sync-prisma-migration-checksums.jsTwo applied migrations were later edited in place, so their SHA-256 no longer matches the value recorded in _prisma_migrations, and Prisma refuses to deploy. The script re-hashes the files and updates the stored checksums inside a transaction (--dry-run supported). It is a deliberate escape hatch that blesses drift — the safer convention, which the repo also follows elsewhere, is a forward-only fix migration.
repair-ui-table-drift.jsA historical rename of fixed.ui_table → fixed.ui_table_columns left older databases in a state Prisma could only fix by a destructive reset. The script performs a non-destructive, transactional repair: rename the table, rename and re-own the identity sequence, restore the column default, re-add the missing FK column, then add the constraint NOT VALID and only VALIDATE it once an orphan check passes. It refuses to guess if both tables exist.

Two generators run on every prisma generate: prisma-dbml-generator, which writes an importable ER model to dbml/awesome.dbml (90 tables — this is the artefact to load into dbdiagram.io), and prisma-docs-generator. The latter's output path, output = "../../docs", resolves outside the repository to the parent workspace directory. That is almost certainly unintended and should be corrected.

8The configured-SQL engine

This is the system's most distinctive subsystem and the one most worth guarding. Grids and dropdowns — their columns, widths, alignment, conditional colouring, totals, and the SELECT that populates them — are rows in fixed.grid_details and fixed.dropdown_details. The server parses SQL it did not write, validates it, binds tenant parameters into it, and executes it on a read-only connection. A new screen is a database row, not a release.

8.1Execution pipeline

8.2Parameter binding

The convention, discovered from the stored rows themselves, is that configured SQL embeds parameters as bare p_-prefixed identifiers. bindGridParams rewrites each token to a PostgreSQL positional parameter and returns the values separately, so nothing is ever concatenated:

// stored in fixed.grid_details.grid_sql
SELECT ls_item_name, ls_qty FROM inventory.item_stock_balance
WHERE ls_comp_id = p_comp_id AND ls_branch_id = p_branch_id

// grid_param = {"p_comp_id":"…","p_branch_id":"…"}   ⇒   bound form:
SELECT … WHERE ls_comp_id = $1 AND ls_branch_id = $2      params = [comp, branch]

Binding order is deterministic (parameter key order); a token appearing many times binds to the same $N; and a key that never appears in the SQL contributes no parameter at all, so an unused parameter is harmless rather than a syntax error.

High — the dropdown path was never migrated to binding

The predecessor of bindGridParams is substituteGridPrm(), which string-concatenates escaped literals into the SQL. It is still live, called from dropdown-details.service.ts:118 with client-supplied parameters. The classic escape is closed — keys are whitelisted by regex, values are restricted to scalars, and single quotes are doubled — but this is manual quoting, not binding, and it will misbehave if a token lands inside a dollar-quoted string or an identifier position. The grid path was fixed; the dropdown path is a regression waiting to be found. Separately, master-lookup.service.ts:859 executes stored dropdown SQL with no parameters at all and swallows failures in a try/catch { continue }. See R3, §15.

8.3Why there is a SQL parser in the codebase

Because the engine must reason about statements it did not author, configured-grid-sql.service.ts contains a small, hand-written, quote- and paren-aware SQL analyser — extractTopLevelSelectClause, splitTopLevelCommaSeparated, extractSqlOutputFieldName, extractTopLevelFromRelation, stripSqlComments. It exists to answer two questions: which output columns does this statement produce (so that grid_columns rows can be matched to them, by explicit mapping or by a scored heuristic), and which relation does it read from (so the stored SQL can be checked against the grid's declared table). This is inherent complexity of the data-driven design, not accidental complexity — but it is the part of the system that most rewards careful test coverage, and it currently has two spec files.

9Transactional integrity and document numbering

9.1Transaction discipline

Interactive Prisma transactions are the dominant write pattern — 294 occurrences across roughly 60 service files. The discipline that makes them compose is a single typing convention: services accept an optional transaction client, so an aggregate write can pull child services into its own transaction.

export type ModuleWriteClient = Prisma.TransactionClient | PrismaService;

// a child service participates in the parent's transaction …
async save(dto: SaveItemPriceDto, tx?: Prisma.TransactionClient) { … }

// … so the composite item save is genuinely atomic
await this.prisma.$transaction(async (tx) => {
  const item = await this.writeItem(dto, tx);
  await this.itemUnitConversionService.syncChildren(item.itemId, dto.unit_conversions, tx);
  await this.itemsPriceMasterService.syncChildren(item.itemId, dto.prices, tx);
  await this.auditLogService.logEntityChange({ … }, tx);   // audit commits with the business write
});

Three consequences follow, and all three are load-bearing. An audit row cannot survive a rolled-back business write, because it is written with the same client. A customer cannot exist without its ledger, because both are created in one transaction. And the child-collection reconciler in item-master-update.service.ts can diff incoming rows against existing ones by natural key — ean_code, iuc_unit_id, ipm_unit_id + ipm_godown_id — and write only genuine deltas, without risking a partially-applied item.

9.2Document numbering under concurrency

ERP document numbers cannot be PostgreSQL sequences: they must reset per fiscal year, be gap-free within a scope, and vary by branch and POS device. The system therefore allocates them with a transaction-scoped advisory lock plus max(n)+1, inside the write transaction:

await client.$queryRaw`
  WITH advisory_lock AS (
    SELECT pg_advisory_xact_lock(
      hashtext(${SEQUENCE_LAST_NO_LOCK_NAMESPACE}),
      hashtext(${this.buildLastNoScopeKey(scope)})   // company|branch|accYear|deviceId
    )
  ) SELECT 1::int AS locked`;

The lock is namespaced and released automatically at commit or rollback — no cleanup path can leak it. The counter itself lives in accounts.acc_voucher_seq, whose uniqueness constraint is the numbering matrix:

@@unique([vchrTypeId, companyId, branchId, accYear, deviceCode, periodKey],
         map: "uq_acc_voucher_seq_scope")
// document type × company × branch × fiscal year × device × reset period

The row also snapshots the applied format (prefix, company code, branch code, zero-pad width, suffix) and caches the last rendered reference. At write time account-voucher-header.helper.ts allocates three numbers per voucher — an internal voucher number, a per-type serial, and the human-readable reference built from them — and re-numbers only when the scope actually changes, so an edit that does not move a voucher across company, branch or year keeps its number. Stock batches use the same idea at a different granularity: generateNextBatchNo() draws its prefix from the batch-prefix master and scopes batch identity by company, branch, godown, item and unit.

Convention — numbering is never a database sequence

If you add a new numbered document, do not reach for SERIAL. Follow the existing pattern: acquire pg_advisory_xact_lock(hashtext(namespace), hashtext(scope)) inside the transaction, take max(n)+1 within the scope, and format from the snapshot columns. A database sequence cannot be reset per year or made gap-free per branch, and mixing the two strategies would silently break the guarantee the ERP relies on.

10Security architecture

This section describes what is enforced, not what is intended. The authentication layer is carefully built — hand-rolled HS256 tokens with strict verification, scrypt password hashing with constant-time comparison, and Redis-backed session revocation. The authorisation layer, by contrast, does not exist: it was removed and not replaced. That asymmetry is the defining fact of the system's current security posture.

10.1Authentication

ControlImplementation
Password storagescrypt (node:crypto), 16-byte salt, 64-byte key, stored as scrypt$<salt>$<hash>. Verification re-derives and compares with timingSafeEqual. Default cost parameters (N=16384, r=8, p=1); no configurable cost and no versioned upgrade path.
Token formatHand-rolled HS256 JWT. @nestjs/jwt is a dependency but unused. Verification rejects alg:none by requiring an exact {alg:'HS256', typ:'JWT'} header, compares the signature with timingSafeEqual, and enforces a custom typ claim (access vs refresh) that prevents token-type confusion. No iss, aud, nbf or jti.
Token lifetimeAccess 900 s; refresh 604,800 s. Refresh re-reads the user, so a disabled account loses access at the next refresh — but refresh tokens are not rotated, and the same token is returned each time.
Session / revocationRedis key auth:session:<sid> holding SHA-256 hashes of both tokens. revokeAccessTokenSession() exists but no route calls it — there is no logout endpoint. Sessions are written with no TTL, so the key space grows without bound.
Device bindingLogin resolves the supplied device_id against the device master; an unregistered, blocked or inactive device is rejected.
LockoutNot implemented. usrFailedLoginCount is incremented on every failure, but no threshold ever sets usrIsLocked — grep confirms the column is never written anywhere in src/. Likewise usrMustChangePassword and usrPasswordExpiresOn are stored but never enforced at login.

10.2Authorisation — the gap

AccessTokenGuard is registered globally as APP_GUARD, so by default every route requires a valid bearer token. Exemption is by the @Public() decorator. That is the entirety of the access-control model. There is no role check, no permission check, and no tenant filter behind it.

What existsWhat is enforced
UserType enum: SUPER ADMIN, ADMIN, MANAGER, USER, CASHIER, VIEWER, SYSTEMNothing. It survives as a JWT claim and a response field. @Roles() and RolesGuard were deleted in commit 80ab8eb.
Per-menu permissions umCanView/Create/Edit/Delete/Print/ExportStored, and returned to the client so it can hide buttons. Never checked server-side. The UI is the only enforcement point.
Company/branch columns on 34–36 modelsNothing. The Prisma tenant-scope extension was deleted with the same commit. getCompanyId() is now referenced in exactly one file, on a write path.
Critical — three compounding exposures

(1) The Users controller is public. src/modules/users/users.controller.ts:36 carries a class-level @Public(). That exposes, with no token at all: POST /users (create a user with a chosen password), GET /users (enumerate all users), PATCH /users/:id (change any user's password) and DELETE /users/delete. This is a full authentication bypass for the whole application — an attacker creates a user, then logs in normally.

(2) Any authenticated user is fully authorised on the remaining ~64 controllers, across all tenants.

(3) Any authenticated user can author server-executed SQL via POST /grid-details/create or POST /dropdown-details/create, then run it. The read-only pool and the deny-list confine it to SELECT, but a SELECT over user_master.usr_password_hash or any other tenant's data satisfies both. If DATABASE_READONLY_URL is unset, that statement runs as the primary application role.

10.3Input validation and transport

Validation is strict and global: whitelist: true strips unknown properties and forbidNonWhitelisted: true turns them into a 400, so mass-assignment is structurally prevented. All 213 DTOs are built from the shared decorator library, which keeps @MaxLength, trimming and UUID-version checks uniform. Two weaknesses stand out: CreateUserDto.user_password carries @IsString() only — no minimum length, no complexity, no maximum (an unbounded input to scrypt) — and LoginAuthDto.ip_address is accepted from the request body and written to the login-session row in preference to the server-observed IP, making session audit IPs attacker-controlled.

10.4The audit trail

Auditing is explicit, not interceptor-driven: 53 services inject AuditLogService and call logEntityChange(input, tx) inside their transaction. Coverage is therefore a matter of developer discipline — a service that forgets the call writes no audit row, and there is no audit of reads or of authentication events.

What is captured is genuinely rich: action (insert|update|approve|cancel), screen, table, primary key, entity id, JSONB before and after snapshots plus a computed field-level diff, actor, branch, and client IP. The audit-screen-sql.constants.ts templates are not executed — they are persisted to audit_screen and parsed to derive source-field → human-label mappings for the read API, which also resolves foreign-key UUIDs back to display names.

High — the audit read API is unscoped

GET /api/v1/audit-logs/list requires a bearer token but applies no company, branch or user filter. Any authenticated user can read every audit row for every tenant — including the JSONB before/after snapshots, which by design contain whatever the audited row contained: PAN and Aadhaar numbers, GSTIN, bank account numbers and IFSC codes, and employee salary fields. This turns the audit trail into the single richest data-exfiltration target in the system. See R4, §15.

11Caching, queues and background work

11.1HTTP response cache

Two global interceptors implement a read-through cache with write-invalidation. HttpCacheInterceptor caches a GET only when the handler carries an explicit @CacheTTL(n > 0); the key is the pathname plus a sorted query string, so ?b=2&a=1 and ?a=1&b=2 share an entry. It sets an X-Cache: HIT|MISS header on every cacheable response, and it swallows all cache errors — a Redis failure degrades to a pass-through, never a 500. HttpCacheInvalidationInterceptor then clears /{prefix}/{version}/{resource}* after any write verb, plus a small table of related resources.

Two cache defects worth fixing together

No tenant dimension in the key. The cache key is URL + query only. Any cached GET is therefore shared across all callers regardless of who they are or which company they belong to. Today the blast radius is limited by the short TTLs below and by the fact that responses are largely tenant-agnostic masters — but it is a cross-tenant data leak waiting for the first company-scoped cached endpoint. (R7)

The default TTL is 3,600× too short. redis.module.ts computes const ttlMilliseconds = ttlSeconds * 1; — evidently intended as * 1000 — and hands the result to a store that expects milliseconds. With REDIS_TTL=3600 the default cache TTL is 3.6 seconds, not one hour. (R8)

Compounding this, roughly 50 controllers declare @CacheTTL(1) — one second — and about twelve use @CacheTTL(60). Comments in configured-grid-sql.controller.ts claim "cache 5 minutes" and "cache 60s" beside a literal 1. In practice the HTTP cache is a one-second de-duplication window for most master endpoints, which is close to no cache at all. The invalidation service also uses Redis KEYS (O(N), blocking) rather than SCAN, once per write request.

11.2Queues

QueueJob and behaviour
audit-log-archivalDeletes audit rows older than olderThanDays (default 365) in batches of 1,000, reporting progress. Retries 3× with exponential backoff.
stock-reconciliationFor a company/year scope, compares each item_batch_stock closing quantity against the summed stock ledger and returns the mismatches. Retries 2×. It detects drift but never repairs it, and it issues one aggregate query per batch row — an N+1 by construction.
Dormant infrastructure

Both queues are registered and both workers run, but nothing enqueues a job. QueueService has no callers outside its own directory; there is no scheduler (@nestjs/schedule is not a dependency) and no controller triggers either job. The archival and reconciliation capabilities exist structurally but have never executed in production. Either wire a schedule to them or remove them — dormant code that appears to provide a guarantee is worse than absent code. (R14)

11.3Redis client

Worth flagging for maintainers: RedisCacheService is a hand-rolled RESP protocol client written directly on node:net/node:tls — it encodes commands and parses + - : $ * replies itself — even though the redis package is already a dependency. It handles reconnection and pending-response queueing, and it is used by the health probe and the auth session store. It has no test coverage.

12Observability and performance

12.1Logging

FileLoggerService extends Nest's ConsoleLogger and appends to two files: logs/app.log (all levels) and logs/error.log (errors and fatals). The format is plain text, not JSON:

2026-07-14T09:12:33.104Z LOG [Bootstrap] DB connected: true
2026-07-14T09:12:41.882Z LOG [RequestLoggerMiddleware] GET /api/v1/items/list 200 - 41.3ms
Medium — logs are unbounded and unjoinable

There is no rotation. No size cap, no retention, no logrotate integration — the streams are opened once and appended to forever. logs/app.log currently stands at 168 MB. Every request writes a line synchronously from the request path. The project's own plan.md claims "app.log / error.log with rotation"; that is not implemented. (R9)

There is no correlation ID. No request id is generated, none is propagated, and none appears in log lines or error responses. Two log lines from the same request cannot be joined, and a user reporting an error has no handle to quote. For a system of this size this is the single highest-leverage observability fix. (R9)

Beyond the log files there is nothing: no metrics endpoint, no tracing, no alerting, and no health signal other than GET /api/v1/health, which probes the database with SELECT 1 and Redis with a real PING, returning ok or degraded (503 when a dependency is down). It does not check memory, event-loop lag, pool saturation or queue depth.

12.2Load testing

scripts/perf/load-test.js is a dependency-free harness (829 lines) with three scenarios — smoke (15 s, 5 concurrent, health only), baseline (60 s, 20 concurrent, an 8-route weighted mix) and stress (180 s, 80 concurrent). It reports throughput, traffic, and min/avg/max/p50/p90/p95/p99 latency using reservoir sampling, and exits non-zero if the failure rate exceeds the scenario's threshold.

The recorded performance baselines are invalid

All three runs stored under logs/perf/ were executed with --accept-status 429, which counts a rate-limit rejection as a success. The stress run reports 780,434 requests at 4,335 req/s with a 100% success rate — but only 2,400 of those responses were HTTP 200. The other 778,034 were 429s. The numbers measure how fast ThrottlerGuard can reject traffic, not how fast the application can serve it.

The system's own docs/performance-load-testing.md §5 documents this trap and prescribes raising THROTTLE_LIMIT for capacity runs. The platform therefore has no valid performance baseline. Re-running the three scenarios with the throttler raised is a one-hour task and a prerequisite for any capacity claim. (R15)

12.3Known performance characteristics

CharacteristicDetail
Connection poolsNeither the Prisma client nor either pg pool sets an explicit connection limit; all three run on defaults. For a single-process deployment this is survivable, but it is untuned.
PaginationOffset-based (skip/take) everywhere, including the configured-SQL engine, which wraps the base query in COUNT(*) plus a LIMIT/OFFSET subquery. Deep pages on large grids will degrade linearly.
Request timeoutA hard-coded 15,000 ms ceiling (REQUEST_TIMEOUT_MS) converts any longer handler into a 408. A slow configured grid will hit this rather than hang.
ConcurrencyPM2 runs a single fork-mode instance — one Node process on one core. There is no clustering and no horizontal scale path today.
Synchronous I/O on the request pathEvery request writes a log line to disk from the request path, and the audit trail adds an insert to every write transaction.

13Build, packaging and deployment

13.1The deployment model

The system is designed to be shipped as a single self-contained executable to hosts that have no Node runtime — the classic on-premise ERP distribution model. npm run release compiles with nest build and then runs pkg, producing erp-server-linux (204 MB) and erp-server-win.exe (196 MB).

The snapshot bundles the compiled output, the generated Prisma client and its native query engine, all 204 migration files, and — notably — the .env file itself. src/main.ts is written to support this: resolveFilePath() detects the pkg runtime and searches the working directory, then the executable's own directory, then the snapshot, so an operator can drop a TLS certificate or a replacement .env beside the binary.

LayerConfiguration
Process managerPM2, ecosystem.config.js: instances: 1, fork mode, autorestart: true, PORT: 3012. The cwd is a hard-coded developer absolute path and must be corrected before any real deployment.
Dependenciesdocker-compose.yml provides Postgres 16 and Redis 7 only — there is no app service. The API runs on the host. Redis is published on 6379 with no password.
Reverse proxyNot in this repository (an nginx config exists one level up in the workspace).
Migrationsnpm run migration:run → prisma migrate deploy. The schema is rebuilt from fragments first, always.
Two packaging hazards

The .env is baked into the binary. It is correctly git-ignored, but pkg.assets lists ".env", so the shipped executable embeds DB_PASSWORD and JWT_SECRET in its snapshot, and falls back to that copy when no external .env is found. Anyone holding the binary holds the secrets. Remove it from assets and require an external file.

The Windows target may have no query engine. Only libquery_engine-debian-openssl-3.0.x.so.node is listed in the bundled assets; there is no query_engine-windows.dll.node. The Windows build must fall back to the WASM/library engine or it will fail at runtime. This should be verified on a clean Windows host before shipping.

14Quality engineering

14.1Test coverage

Fifty-six unit spec files and two end-to-end specs. The tests that exist are well-formed — plain Jest with hand-rolled doubles, constructing the class directly rather than booting a Nest testing module — but they are concentrated almost entirely in one module. Two-thirds of all specs test Inventory.

14.2Continuous integration

Medium — there is no CI pipeline

.github/ contains one file: copilot-instructions.md. There is no .github/workflows/ directory and no CI configuration of any kind anywhere in the repository. Nothing runs lint, typecheck, tests or the build automatically. The npm scripts all exist (lint, typecheck, test, test:cov, test:e2e, build) and must be invoked by hand. There are also no coverage thresholds configured in Jest. The project's own README lists this as an open item. (R10)

The end-to-end suite boots the full AppModule through Test.createTestingModule, re-applies the validation pipe, versioning and prefix, and exercises /api/v1/health with supertest. It asserts a status of either 200 or 503 — that is, it tolerates a dead database — so it verifies wiring rather than behaviour.

16Remediation roadmap

Sequenced by dependency and risk, not by module. P0 is the set of changes without which the system should not be exposed to untrusted networks; each is small and well-localised.

16.1P0 — before any production exposure

16.2P1 — operational readiness

  • Introduce a correlation ID (R9). Generate one per request in RequestContextMiddleware, put it in the ALS store, include it in every log line and in both error envelopes, and echo it as X-Request-Id. This is a half-day change that makes every future incident tractable.
  • Rotate logs (R9) — size-capped rotation with retention, and move the request log off the synchronous request path.
  • Add a CI pipeline (R10): lint, typecheck, unit tests, build, and a migration check on every pull request. Set a coverage floor and ratchet it.
  • Fix the cache tier (R7, R8): correct the millisecond conversion, add the user/company dimension to the cache key, replace KEYS with SCAN in the invalidator, and set TTLs that reflect the comments' intent.
  • Gate Swagger behind an environment flag or basic auth in production (R11), and scope 'unsafe-inline' to the docs route.
  • Re-establish a performance baseline (R15) with the throttler raised, and record it as the reference for future regressions.

16.3P2 — architectural consolidation

  • Unify the error envelope (R12) — a single global filter, one shape, statusCode and correlation id always present. Delete the 55 per-module filters, which currently differ only in a regular expression used to guess field names.
  • Migrate the dropdown path to bindGridParams and delete substituteGridPrm (R3), so no code path concatenates values into SQL.
  • Resolve the queues (R14): schedule the archival and reconciliation jobs, or remove them. Make the reconciliation processor set-based rather than row-by-row.
  • Extend test coverage to the configured-SQL engine, the auth guard, the cache interceptors and the stock ledger — the four subsystems where a silent defect is most costly.
  • Housekeeping: delete the orphaned item-price-details module; remove .env from pkg.assets; reconcile the three conflicting default values for THROTTLE_LIMIT and PORT; fix the prisma-docs-generator output path; verify the Windows query engine.
Closing assessment

The domain engineering here is strong and, in places, genuinely sophisticated — the stock ledger, the voucher numbering, the linked-ledger invariant and the configured-SQL engine are all the work of someone who understands the problem. The gaps are almost entirely in the surrounding envelope: authorisation, isolation, observability and automation. That is a fortunate shape for a codebase to have, because the envelope is where fixes are cheapest. The P0 list above is perhaps a week of focused work, and most of it is restoring code that already existed.
